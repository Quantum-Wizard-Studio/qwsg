# Framework 2.0 Retrospective: Tasks 057–061

Tasks 057–061 proved both the value and the cost of Framework 1.1.0.

- Task 057's 26-checkpoint style fragmented one acceptance into many Owner
  interactions. V2 uses one approved practical run and one bounded diagnostic
  runner when private/external action is inherently Owner-side.
- Tasks 059 and 061 turned recoverable observations and late evidence into STOP
  candidates. V2 classifies first and preserves trustworthy evidence across
  reporting chronology.
- Task 059 correctly stopped when candidate correction would have modified
  frozen RC.5 bytes. Candidate immutability remains mandatory.
- Task 060 correctly kept diagnose/fix/regression/retest inside one development
  task. V2 makes that the default rather than exceptional authority text.
- Task 061 initially imposed persistent notification readiness beyond the
  product contract. V2 requires contract comparison and classifies this as an
  acceptance defect or expected behavior before product modification.
- Repeated shell fragments made the Owner a manual diagnostic engine. V2's
  bounded runner consolidates checks, verifies its identity, limits output and
  time, classifies the result, and cleans up.

For a comparable ordinary defect, v1 commonly required an initial approval,
several result-relay interactions, a STOP decision, and sometimes a new task.
V2 targets one approval and one final result; only credentials, physical
actions, external access, or genuine boundaries add interactions. This removes
several routine Owner round trips without weakening any release or safety gate.
